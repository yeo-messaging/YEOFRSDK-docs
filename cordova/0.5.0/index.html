YEOFR for Cordova

This guide is for plugin 0.5.0 (iOS engine 0.11.2, Android engine 0.2.29).

On-device face recognition with liveness for Cordova apps on iOS and Android, with the same TypeScript API as the Capacitor plugin.

This guide takes an Ionic Angular app on Cordova from install to a working face screen: install, the config.xml settings, the transparent page, a small Angular transport, what each status means, enrolment, licensing and troubleshooting. The plugin itself has no Angular dependency; the Angular code here is one way to use it.

iOS and Android. Plugin 0.5.0 supports both. iOS needs iOS 17.0 or later on an iPhone, and the app's deployment-target must say so; see iOS.

Recognition needs a real phone. The app builds for the Android emulator and, on an Apple Silicon Mac, for the iOS Simulator, but neither gives the engine a real face, so results stay at noFace. That is expected, not a fault.

What you get

Piece Version Where it comes from
Cordova plugin @yeomessagingcom/cordova-plugin-yeofr 0.5.0 npm, through cordova plugin add
Android engine com.yeomessaging:yeofr-android 0.2.29 Maven, from the private YEO repository, with credentials YEO gives you
iOS engine YEOFR 0.11.2 GitHub, from the public YEOFR-SPM package; see iOS; native reference: https://yeo-messaging.github.io/YEOFRSDK-docs/0.11.2/documentation/yeofr/

The plugin pins both engine versions. getVersion() returns the engine version (0.2.29 on Android, 0.11.2 on iOS), not the plugin version.

How it works:

  • The native layer owns the camera. It draws the preview in a native view behind the WebView.
  • Your page is transparent where the camera should show, and draws its own overlay: prompts, buttons, progress.
  • Only small JSON events reach JavaScript. Frames never do.
Event When
result Every analysed frame while the camera runs: the trust status for the face in view.
enrolProgress Every analysed frame while an enrolment capture is running.
registered An enrolment capture finished and the face is stored.
error Something failed after start() resolved.

Frameworks. The plugin is framework-agnostic: any web framework running in a Cordova app uses the same API, whether Angular, React, Vue or plain JavaScript, with or without Ionic. The examples are Angular because the first client is.

Limits of this release:

  • One camera session per app at a time.
  • Continuous status only. There is no one-shot check call yet.
  • Portrait only. The preview does not follow device rotation, so lock the app to portrait (<preference name="Orientation" value="portrait" /> in config.xml).
  • No browser build. Outside the Cordova app (for example ng serve) there is no cordova object and no plugin, so unit tests use a fake transport.

Capacitor or Cordova

Capacitor apps install the Capacitor plugin, @yeomessagingcom/capacitor-yeofr; Cordova apps, including Ionic apps still on Cordova, install this one. Both wrap the same native layer and the same TypeScript contract, so the Angular code is shared and only the transport differs.

If your project has a config.xml and a platforms/ folder at its root, it is a Cordova app and this is your guide. If it has capacitor.config.ts or capacitor.config.json, follow the Capacitor guide instead.

Requirements

Android iOS
Cordova platform cordova-android 14 (recommended); 13 with one extra preference cordova-ios 8 (recommended, Swift package) or 7 (classic, engine downloaded at plugin add)

Device A real phone with Google Play services A real iPhone
Build machine JDK 17 or later; Android SDK platform 36; a gradle binary on the PATH (Homebrew gradle, or the one Android Studio ships) A Mac with Xcode 26 or later; network access to GitHub; an Apple Silicon Mac for Simulator builds
Credential Pilot code Licence file (preferred) or pilot code

Google Play services is required on Android because the face detector the engine uses is delivered through it. The Android native libraries are 16 KB page-aligned, as Google Play requires for apps targeting Android 15 and later. Apps that target Android 11 and later are well inside this range.

cordova-ios 8 itself needs Xcode 16.4 or later; the plugin's Swift sources and the engine need Xcode 26 or later, as for the Capacitor plugin. The iOS builds were verified with Xcode 27 only. The engine's Simulator slice is arm64 only, so Simulator builds need an Apple Silicon Mac; Intel Simulators are not supported.

cordova-android 12 and older are not supported; see cordova-android 12 and older.

Install

cordova plugin add @yeomessagingcom/cordova-plugin-yeofr

Cordova installs the package into node_modules/, records it in package.json and copies it into each platform the app has. iOS is described under iOS. On Android the plugin brings:

  • two prebuilt AARs, the core and the Cordova adapter, into platforms/android/app/libs/. They are compiled for Java 17;
  • a Gradle fragment that adds the private YEO Maven repository and the dependencies the AARs need: the engine com.yeomessaging:yeofr-android:0.2.29, CameraX 1.5.3, androidx.core 1.17.0 and the Kotlin 2.4.21 standard library.

Your app does not need the Kotlin Gradle plugin, and you do not edit any Gradle file. The camera permission is declared in the core AAR's manifest; start() asks the user for it when it has not been decided yet.

Android then needs three things, once per app.

1. Credentials for the YEO repository

The Android engine is in a private Maven repository. The plugin's Gradle fragment reads its URL and login from your machine, never from the project. Put the URL and login YEO gave you in ~/.gradle/gradle.properties on each developer machine:

yeoRepositoryUrl=<the repository URL YEO gave you>
yeoUser=<your user>
yeoPassword=<your password>

On CI, set YEO_REPOSITORY_URL, YEO_USER and YEO_PASSWORD as secret environment variables instead. Never commit any of them. The build stops with a message naming these settings when the URL is missing.

2. The config.xml preferences

The engine depends on androidx.core 1.17, which needs Android Gradle Plugin 8.9.1 or later and compileSdk 36. The cordova-android templates default to older values, so raise them in config.xml.

cordova-android 14. Add these under <platform name="android">:

<platform name="android">
    <preference name="android-minSdkVersion" value="24" />
    <preference name="android-compileSdkVersion" value="36" />
    <preference name="AndroidGradlePluginVersion" value="8.9.1" />
    <preference name="AndroidJavaSourceCompatibility" value="17" />
    <preference name="AndroidJavaTargetCompatibility" value="17" />
</platform>
Preference Value cordova-android 14 default Why
android-minSdkVersion 24 24 The plugin's minimum; set it so a later template change cannot lower it.
android-compileSdkVersion 36 35 androidx.core 1.17 is compiled against API 36.
AndroidGradlePluginVersion 8.9.1 8.7.3 androidx.core 1.17 declares 8.9.1 as its minimum. Gradle 8.13, the template's default, runs it.
AndroidJavaSourceCompatibility, AndroidJavaTargetCompatibility 17 11 The AARs are Java 17 bytecode.

Cordova applies the preferences when it prepares the platform, which cordova build android does first.

cordova-android 13. Add the same five preferences, plus the Gradle version:

<preference name="GradleVersion" value="8.13" />

cordova-android 13 defaults to Android Gradle Plugin 8.3.0, compileSdk 34, Java 8 and Gradle 8.7. Gradle 8.7 is too old to run Android Gradle Plugin 8.9.1, so the build fails until GradleVersion is raised. Its default android-targetSdkVersion of 34 can stay; that is how it was verified.

cordova-android 12 and older

Not supported, and not tested. Their templates pin Gradle 7.6 and Android Gradle Plugin 7.4, which cannot load androidx.core 1.17 (it declares a minimum Android Gradle Plugin of 8.9.1) or compileSdk 36, so dependency resolution would fail before any code compiles; and AndroidGradlePluginVersion cannot lift the plugin past what their Gradle wrapper supports. That follows from the templates' pinned versions; it was not tested. Move the app to cordova-android 14 first. The plugin declares cordova-android >=13.0.0 as its engine, so the Cordova CLI reports the mismatch when it installs the plugin.

3. JDK 17 or later

Run the Cordova build with a JDK 17 or later as JAVA_HOME. cordova-android 14 needs it anyway, and the plugin's AARs are Java 17 class files, which an older JDK cannot read.

iOS

On iOS the plugin brings its Swift sources, the core and the Cordova adapter, and the engine, YEOFR 0.11.2. How the engine arrives depends on the cordova-ios version. CocoaPods is not used with either: the plugin has no <podspec>, and none is planned, because the CocoaPods trunk becomes read-only on 2 December 2026.

Both versions need the deployment target in config.xml. The plugin and the engine need iOS 17.0, and the cordova-ios templates default lower (13.0 on cordova-ios 8, 11.0 on cordova-ios 7):

<platform name="ios">
    <preference name="deployment-target" value="17.0" />
</platform>

Set it before cordova platform add ios. Cordova applies it when it creates the platform, and cordova prepare does not apply a preference added later, so an app that already has the iOS platform removes it and adds it again (cordova platform rm ios, then cordova platform add ios). Without it the build stops with a minimum platform version error; see Troubleshooting.

cordova-ios 8 (recommended)

cordova-ios 8 builds the plugin as a Swift package. cordova plugin add copies it into platforms/ios/packages/ and registers it in platforms/ios/packages/cordova-ios-plugins/Package.swift. Swift Package Manager then resolves the engine from the public YEOFR-SPM package on GitHub at exactly 0.11.2. No login is needed, and the plugin downloads nothing itself.

Nothing else is needed beyond the deployment-target above and, if you want your own wording, the camera usage string. Build with cordova build ios --device, or cordova build ios --emulator on an Apple Silicon Mac.

cordova-ios 7

Use cordova-ios 8 where you can; cordova-ios 7 needs two build settings on a current Xcode that the plugin cannot set for you (below). cordova-ios 7 has no Swift package support, so the plugin uses its classic entries. During cordova plugin add, the plugin's install hook:

  1. reads the engine version the plugin pins, 0.11.2;
  2. downloads YEOFR.xcframework.zip (138 MB) from the YEOFR-SPM release on GitHub into ~/.cache/yeofr-cordova/, unless a copy with the right checksum is already there;
  3. checks the archive's SHA-256 against the checksum in YEOFR-SPM's Package.swift;
  4. unpacks it with ditto, which is part of macOS.

Cordova then adds YEOFR.xcframework (embedded) and the plugin's 18 Swift source files to the app target. The sources compile in Swift 5 mode.

The first add therefore needs a Mac with network access to GitHub: the hook reads the checksum from raw.githubusercontent.com on every add, and downloads the archive from GitHub's release storage when it is not cached. Later adds reuse the cached archive. The hook logs what it did, for example fetch-ios-engine: YEOFR 0.11.2 downloaded to … or … cached at ….

On Xcode 27 the cordova-ios 7 template itself needs two more settings:

  • the Swift version, in config.xml under <platform name="ios">:

    <preference name="SwiftVersion" value="5.0" />

  • a deployment target of at least 15.0 for CordovaLib, which the deployment-target preference does not reach. Pass it to the build:

    cordova build ios --device -- --buildFlag="IPHONEOS_DEPLOYMENT_TARGET=17.0"

The camera usage string

On both cordova-ios versions the plugin writes NSCameraUsageDescription into the app's Info.plist. The default text is "The camera is used to recognise your face and check that you are present." Word it for your app when you add the plugin:

cordova plugin add @yeomessagingcom/cordova-plugin-yeofr \
  --variable CAMERA_USAGE_DESCRIPTION="We use the camera to check that it is you."

Cordova records the variable in package.json, so later installs keep it. To change it, remove the plugin and add it again with the new text. iOS ends any app that opens the camera without a usage string, so do not remove it.

Make the page transparent

The preview is a native view behind the WebView. Anything on the page with a solid background covers it. While the camera runs, the plugin makes the WebView itself transparent; your page must be transparent too.

Make the page transparent only while the face page is showing, so the rest of your app keeps its theme. Add this to your global styles (src/global.scss or src/styles.scss):

body.yeofr-camera {
  --ion-background-color: transparent;
  background: transparent;

  ion-app {
    background: transparent;
  }
}

The face page adds the yeofr-camera class to <body> when it enters and removes it when it leaves, exactly as in the Capacitor guide's page. Give your overlays a translucent background, not a solid one. On stop() the plugin puts the WebView's own background back: on Android the BackgroundColor preference from config.xml, or white when none is set; on iOS the web view's opacity and colours as they were before start().

Ionic Angular quick start

The Angular code is the same as in the Capacitor guide, split into three parts:

  • FaceTransport: a small interface over the plugin. The service depends only on it.
  • FaceService: owns the session and turns events into signals and plain words.
  • FacePage: starts the camera when the page enters and stops it when the page leaves.

Only the transport is Cordova's own. This section shows it and the one provider line that selects it, and points at the Capacitor guide for the rest, which you copy unchanged apart from two import lines.

The code is written for Angular 18 and Ionic 8 with standalone components. Angular 18 is out of long-term support; on a newer Angular the code is the same.

The files go in src/app/face/.

1. The transport interface

face-transport.ts is the file from the Capacitor guide's transport section, with the types imported from this package:

import type {
  ActivateOptions,
  EnrolOptions,
  StartOptions,
  YeofrEventMap,
  YeofrEventName,
} from '@yeomessagingcom/cordova-plugin-yeofr';

cordova plugin add puts the package in node_modules/, so TypeScript finds its types there. import type keeps it out of your bundle; Cordova loads the plugin's JavaScript itself.

2. The Cordova transport

cordova-face-transport.ts:

import { Injectable } from '@angular/core';
import type {
  ActivateOptions,
  EnrolOptions,
  StartOptions,
  YeofrEventMap,
  YeofrEventName,
  YeofrPlugin,
} from '@yeomessagingcom/cordova-plugin-yeofr';

import type { FaceTransport, Unsubscribe } from './face-transport';

declare const cordova: { plugins: { Yeofr: YeofrPlugin } };

@Injectable()
export class CordovaFaceTransport implements FaceTransport {
  private plugin: Promise<YeofrPlugin> | null = null;

  async activate(options: ActivateOptions): Promise<void> {
    return (await this.yeofr()).activate(options);
  }

  async start(options?: StartOptions): Promise<void> {
    return (await this.yeofr()).start(options);
  }

  async stop(): Promise<void> {
    return (await this.yeofr()).stop();
  }

  async enrol(options: EnrolOptions): Promise<void> {
    return (await this.yeofr()).enrol(options);
  }

  async clearTracker(): Promise<void> {
    return (await this.yeofr()).clearTracker();
  }

  async isEnrolled(): Promise<boolean> {
    const { tracker } = await (await this.yeofr()).getTrackerData();
    return tracker !== '';
  }

  async on<E extends YeofrEventName>(
    event: E,
    listener: (event: YeofrEventMap[E]) => void,
  ): Promise<Unsubscribe> {
    const handle = await (await this.yeofr()).addListener(event, listener);
    return () => handle.remove();
  }

  // Cordova sets up cordova.plugins only once deviceready has fired.
  private yeofr(): Promise<YeofrPlugin> {
    this.plugin ??= new Promise((resolve) => {
      document.addEventListener('deviceready', () => resolve(cordova.plugins.Yeofr), {
        once: true,
      });
    });
    return this.plugin;
  }
}

Angular usually starts before deviceready, so the transport waits for it once and then forwards every call. A deviceready listener added after the event has fired still runs straight away, so the order does not matter.

3. Credentials and providers

Follow the Capacitor guide's credentials and providers section for environment.ts, app.config.ts and app.routes.ts, with two changes in app.config.ts: import IonicRouteStrategy and provideIonicAngular from @ionic/angular/standalone, and provide the Cordova transport:

{ provide: FACE_TRANSPORT, useClass: CordovaFaceTransport },

with import { CordovaFaceTransport } from './face/cordova-face-transport';. Android uses the pilot code and iOS the licence file; pass both, so the same call works on each.

4. The service and the page

Copy face.service.ts from the Capacitor guide's service section and face.page.ts, face.page.html and face.page.scss from its page section, read the notes there, and make these changes for Angular 18 and Cordova:

  • In face.service.ts, import the types from @yeomessagingcom/cordova-plugin-yeofr instead of @yeomessagingcom/capacitor-yeofr.
  • In face.page.ts, import the Ionic components and the ViewDidEnter and ViewWillLeave types from @ionic/angular/standalone, and add standalone: true to the @Component decorator.

Nothing else changes. Unit tests inject a fake FaceTransport, as with Capacitor.

Run it

index.html must load Cordova's script, which Cordova adds to www/ at build time:

<script src="cordova.js"></script>

Point Angular's build output at www/, the folder Cordova packages: in angular.json, set "outputPath": { "base": "www", "browser": "" } and "baseHref": "./". Then:

npx ng build
cordova run android --device

On iOS, set a signing team on the App target first (open the workspace in platforms/ios/ in Xcode), then cordova run ios --device. The transport and the rest of the Angular code are the same on both platforms.

Open /face/<an id>, allow the camera, tap Enrol my face, follow the prompts, and the prompt changes to Verified.

The plugin object

The plugin has the same methods, options, events, error codes and enums as the Capacitor plugin. The Capacitor guide and the API section of the plugin's README describe each call; this section lists only what is Cordova's own.

  • Access. The plugin is cordova.plugins.Yeofr, available after deviceready. Before that event it is undefined.
  • Types. import type { YeofrPlugin, ResultEvent, ... } from '@yeomessagingcom/cordova-plugin-yeofr'. The package also adds Yeofr to CordovaPlugins for apps that use @types/cordova.
  • Rejections. Every call returns a promise. A rejection is an Error with a code from YeofrErrorCode and a message with native detail for your logs.
  • Listeners. addListener(event, listener) resolves to a handle with remove(): Promise<void>; removeAllListeners() removes them all. The plugin opens one native event channel with the first listener and closes it when the last one is removed. A listener that throws is logged and does not stop the others.
  • Page loads. A page reload or navigation in the WebView stops the native session and closes the event channel, so no camera runs behind a page that no longer knows about it. The new page subscribes again and starts the camera when its face page enters. Router navigation inside an Angular app does not load a page.
  • Permissions. requestPermissions() and start() ask for the camera. On Android checkPermissions() reports granted or prompt, because Android cannot tell a refused permission from one never asked until it asks again; requestPermissions() reports denied when Android will not show the prompt again. On iOS checkPermissions() also reports denied: iOS asks once, and after a refusal the user must allow the camera in Settings.
document.addEventListener('deviceready', async () => {
  const yeofr = cordova.plugins.Yeofr;
  await yeofr.activate({ pilotCode });
  const results = await yeofr.addListener('result', (r) => console.log(r.status));
  await yeofr.start();
  // later
  await yeofr.stop();
  await results.remove();
});

What the statuses mean

Each result event carries one fused decision in status. Act on trusted only; the other fields explain it.

status Meaning What to show
noFace No face in view. "Show your face"
badFraming A face is in view but cannot be used: too far, too close, more than one face, or badly placed. The framing hint: tooFar "Move closer", tooClose "Move back", multipleFaces "One face at a time", otherwise "Adjust your position".
notTrusted A usable face that is not the enrolled person, or is the enrolled person but has not passed liveness. See below.
trusted The enrolled person, live. Your success state.

notTrusted covers three situations. Tell them apart like this:

Situation How to tell What to show
Recognised, not live yet matchedName is set and isLive is false "Hold still and look at the camera". Liveness takes a moment after a face appears. If it lasts more than about 2 seconds, "Not a live face".
Someone else matchedName is null and someone is enrolled "Not recognised"
Nobody enrolled yet matchedName is null and nobody is enrolled "Face found", and offer enrolment

Do not build your own rule from the other fields. trusted is the rule. The Capacitor guide describes the other fields, the rejection codes and the error events; they are the same here, platform notes included. On iOS confidence is always null, depthIsThreeD carries the TrueDepth result on iPhones that have the sensor, and badFraming can come with framing: 'valid', so show a general hint then. Never show message to the user.

Enrolment and the pose walk

Enrolment stores one person's face on the phone, under a name you choose. Call enrol() while the camera runs:

await Yeofr.enrol({
  name: customerId,
  poses: ['front', 'yawLeft', 'yawRight', 'pitchUp', 'pitchDown'],
});

Or arm it with the start, which is the same as calling enrol() right after start() resolves:

await Yeofr.start({ enrolName: customerId, poses: ['front', 'yawLeft', 'yawRight'] });

Here Yeofr is cordova.plugins.Yeofr. customerId is stored on the phone with the face template and comes back as matchedName, so use an identifier your app already has rather than personal data.

The pose walk. poses is the list of head positions to prompt for, in order. Omit it for a single front capture. More poses put more angles in the gallery, which helps recognition when the head moves. The engine cannot measure head pose, so the prompts guide the user; they do not gate the capture. Android spreads the capture evenly across the poses; iOS runs one capture per pose, with a short pause before each so the user can move.

Progress. While a capture runs, every analysed frame sends enrolProgress:

Field Use
phase capturing, then completed (followed by registered) or failed.
pose What the user should be doing now. Your app owns the wording.
posesAccepted, posesPlanned Progress through the walk, for a progress bar.
isTargetMatched This frame passed the capture checks (framing and liveness). Show "Hold that pose".

When registered arrives, the face is stored and the next result events can be trusted. On Android, if the face cannot be saved, an error event with storageFailed follows registered. On iOS a failed capture sends enrolProgress with failed, then an error event with enrolFailed.

One identity at a time. A capture replaces the enrolled identity. If a capture is cut short, by stop(), a new enrol(), the app going to the background on iOS, or a page reload, the previous enrolment is put back as it was. Nothing half-enrolled stays recognisable.

Backgrounding. On iOS, sending the app to the background ends a running capture (enrolProgress failed, then error enrolFailed); start it again when the user returns. On Android a capture stays armed while the app is in the background and carries on when the camera resumes.

Storage. By default the plugin keeps the enrolled face template in the app's private\nstorage, out of device backups (on iOS also under file protection), restores it when\nactivate() runs, and removes it on clearTracker(). The template is stored as the\nengine writes it; the plugin does not encrypt it. We recommend storing it encrypted:\nread it with getTrackerData() once registered has arrived, keep it in a store of\nyour choosing (encrypted at rest with your own key management, or on your backend), and\nput it back with loadTracker() before start(). Where and how you keep it is your\ndecision; the plugin supports both the default storage and a host-held template.

Licence handling

The engine needs a credential before it does anything. There are two kinds:

Credential What it is Platforms
Licence file A signed .yeolicense file issued for your iOS bundle id. Pass its bytes as base64 in licence. iOS only
Pilot code A time-limited code issued by YEO. Pass it as pilotCode. Android (the only credential); iOS fallback

Pass both in one call. Each platform takes the one it uses: iOS uses the licence when one is given, and Android ignores the licence.

await Yeofr.activate({ licence: licenceBase64, pilotCode });

Use a licence file on iOS. A licence the engine refuses rejects activate() with activationFailed and the reason (expired, bundleIDMismatch, and so on). Your app stays up and can show a message.

An invalid or expired pilot code closes the app on iOS. The engine ends the process during activate(). The promise does not reject, so try/catch does not help. To your users it looks like a crash when the face screen opens. If your iOS app closes at that moment, check the pilot code first, and ship iOS builds with a licence file.

On Android, a pilot code the engine refuses rejects with activationFailed. A licence alone, or no credential at all, rejects with badInput.

Pilot codes expire. Do not hard-code one in shipped source: load it from build configuration or from your backend, so a new code does not need a new binary. Ask YEO for a code that covers your whole test period, and check it on both platforms. Licence files and pilot codes come from YEO support.

App shielding and hardening products

The plugin needs nothing special from app shielding or hardening products, but they change the app the camera runs in. Develop and measure on unshielded builds, run acceptance on a shielded build of the same commit on real phones, expect screenshots of the face page to come out black, and when something works unshielded but fails shielded, send the error codes from both builds to your shielding vendor and to YEO. The Capacitor guide's shielding section has the full checklist.

If only the large download is blocked, save YEOFR.xcframework.zip from the YEOFR-SPM 0.11.2 release as ~/.cache/yeofr-cordova/YEOFR-0.11.2.xcframework.zip; the hook uses a cached archive whose checksum matches, but it still reads the checksum from raw.githubusercontent.com.
cordova-ios 7: fetch-ios-engine: …: sha256 …, expected … The download arrived incomplete or altered, often by a proxy that rewrites downloads. Delete ~/.cache/yeofr-cordova/YEOFR-0.11.2.xcframework.zip if it is there, then remove the plugin and add it again. If it keeps failing, download from a network without the proxy.
cordova-ios 7: fetch-ios-engine: needs macOS (ditto), or spawnSync ditto ENOENT The hook unpacks the engine with ditto, which is part of macOS at /usr/bin/ditto. Add the iOS plugin on a Mac with /usr/bin on the PATH.
iOS: compile errors in the plugin's Swift files, or failed to build module 'YEOFR' naming a newer Swift compiler Xcode is older than 26. The plugin's sources and the engine need Xcode 26 or later on both cordova-ios versions. Install it and select it with xcode-select.
iOS Simulator build: missing architecture(s) required by this target (x86_64) The engine's Simulator slice is arm64 only, and the build includes the Intel Simulator. Build for the Simulator on an Apple Silicon Mac with cordova build ios --emulator, which builds the active architecture only. Intel Simulators are not supported; test on an iPhone.
cordova.plugins.Yeofr is undefined The call ran before deviceready, or index.html does not load cordova.js. Use the transport, which waits for deviceready, and add the script tag from Run it.
iOS app closes when the face page opens An invalid or expired pilot code (see Licence handling), or NSCameraUsageDescription is missing from the app's Info.plist. iOS ends any app that opens the camera without it. The plugin adds it when it is installed; if it is missing, remove the plugin and add it again, and check that no other edit-config in config.xml removes it.
Android phone: the camera shows but results stay noFace Check that Google Play services is installed and up to date. Phones without Google Play services are not supported.
Simulator or emulator: results stay noFace Expected. Neither gives the engine a real face. Test on phones.
start() rejects permissionDenied The user refused the camera. iOS asks only once; after that the user must allow it in Settings. Android stops asking if the user chose not to be asked again; they must then allow it in Settings. checkPermissions() tells you the state before you start.
The camera runs but the screen is white or your theme colour Something opaque covers the preview: the yeofr-camera class is not on <body>, or an element has a solid background. See Make the page transparent.
The camera stops after a page reload By design. Loading a page stops the native session, so no camera runs behind a page that no longer knows about it, and the old listeners are gone. The new page subscribes and starts the camera again when it enters.
alreadyRunning start() ran while a session was running. There is one camera session per app: two pages each starting the camera, or a start without a stop. Keep the session in one service, as FaceService does. On iOS, activate() and loadTracker() also reject alreadyRunning while a session runs.
The preview is sideways The preview does not follow rotation in this release. Lock the app to portrait.
registered never arrives The capture only counts frames that pass framing and liveness. Fill the frame, hold still, use good light.
