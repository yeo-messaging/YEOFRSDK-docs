YEOFR for React Native

On-device face recognition with anti-spoof liveness, for iOS and Android, from one JavaScript API.

This is the complete integration reference: install, licensing, the full API, the platform differences that matter when you design your screens, and how to run the sample app. For the meaning of the native trust concepts underneath — PADVerdict, SpoofReason, FaceFramingStatus, liveness fusion — see the native reference at https://yeo-messaging.github.io/YEOFRSDK-docs/documentation/yeofr/.

Recognition needs a real device. The package builds and runs in the iOS simulator, so your app still compiles and your tests still run, but activate there rejects with E_UNAVAILABLE_SIMULATOR. That is expected, not a fault.

What you are integrating

Piece Version Where it comes from
React Native bridge @yeomessagingcom/react-native-yeofr npm (public)
iOS engine YEOFR 0.7.8 Swift Package — YEOFR-SPM, added to your app target
Android engine com.yeomessaging:yeofr-android 0.1.24 Maven, from the Repsy repo, pulled in transitively

The bridge pins both engine versions — npx yeofr-setup doctor prints the pair it expects, so that output is always authoritative for the version you have installed.

Requirements: React Native 0.81+, iOS 17.0 minimum, Xcode 26, an Apple-silicon Mac (the xcframework has no Intel simulator slice), Android minSdk 24.

Use 0.4.2 or later. Earlier releases are deprecated — they predate the frame API and the setup script, and anything before 0.4.1 also predates the Android capture pipeline moving into the bridge. Do not start a new integration on one.

The Android engine is pinned to 0.1.24 deliberately. A newer 0.2.x line exists on Maven, which splits CameraX out of the engine into a separate module; the bridge does not use it, because the bridge already owns capture on Android. Let the bridge resolve its own engine version rather than forcing one.

getVersion() returns the engine version — 0.7.8 on iOS, 0.1.24 on Android — not the bridge version. That is intentional: it is the number that determines recognition behaviour.

Quick start — from an empty folder

The condensed path from nothing to recognition running on phones. Each step links to the section with the full detail.

Machine setup, once — React Native's Android tooling needs these in your shell (~/.zshrc), or you get adb: command not found and Unable to locate a Java Runtime:

export ANDROID_HOME="$HOME/Library/Android/sdk"
export PATH="$ANDROID_HOME/platform-tools:$PATH"
export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"

Project:

npx @react-native-community/cli@latest init MyApp --version 0.81.0   # CocoaPods prompt: No
cd MyApp                       # install INSIDE the project — the parent folder is a classic miss
npm i @yeomessagingcom/react-native-yeofr
npx yeofr-setup                # the whole native install, then pod install
npx yeofr-setup doctor         # every line should read "ok"

Do not run npm audit fix --force, however hard npm suggests it. The advisories are all in React Native's build-time tooling and never ship in your app; --force "fixes" them by downgrading react-native and this package to broken versions. Recovery if it happened: git checkout -- package.json package-lock.json && rm -rf node_modules && npm install.

iOS signing, once per project — a fresh app has no team and the CLI fails with the unhelpful xcodebuild exited with error code '70': open ios/MyApp.xcworkspace, MyApp target → Signing & Capabilities → tick Automatically manage signing, pick your Team. First device build also wants the phone unlocked, "Trust This Computer" accepted, and Developer Mode enabled (Settings → Privacy & Security).

Smoke test — replace App.tsx with a screen that calls getVersion() and activate({pilotUnlockCode}) and renders the result (see Verify the install). Get a pilot code first — an invalid or expired one terminates the iOS app at launch.

Run — two terminals, both in the project:

npm start                      # 1: Metro, leave running
npm run ios -- --device        # 2: iPhone plugged in and unlocked
npm run android                # 2: Android

With several iPhones attached --device grabs the first — pin yours with npm run ios -- --udid <UDID> (xcrun xctrace list devices). Expected on screen: engine 0.7.8 (iOS) / 0.1.24 (Android), activated. After that, saving a JS file reloads the app via Metro; rebuild only when something native changes.

Quick start — the example app

The repo's demo (YeofrDemo: activate → enrol → recognise) from clone to phone. Same machine setup as above, plus Homebrew Ruby for the repo's pinned bundler (see Running it for the one-time gem install).

git clone git@github.com:yeo-messaging/react-native-yeofr.git
cd react-native-yeofr
npm install                         # root install — the example is an npm workspace
cd example                          # everything after this runs from example/
npx yeofr-setup                     # validates the config, runs pod install

Put a real pilot code in example/App.tsx (the XXXX-… placeholder kills the iOS app at activation; Android just shows Unlicensed). iOS signing is pre-configured with the YEO team — pick your own in Signing & Capabilities only if you are not on it. Do not rename the bundle ids: the SDK entitlement is keyed to com.youreyeonly.*.

npm start                           # terminal 1 — Metro
npm run ios -- --device             # terminal 2 — iPhone
npm run android                     # terminal 2 — Android

Expected: the Hub shows YEOFR Pilot · Activated, footer YEOFR SDK 0.7.8 / 0.1.24. Type a name → Enrol Face (grant the camera permission; hold the phone up normally — flat on a desk it films the ceiling and reads as badly framed or spoof) → Live Recognition shows the green trusted badge. Install

npm i @yeomessagingcom/react-native-yeofr

Autolinking registers the native module on both platforms. It cannot do the two native steps that follow — neither npm nor autolinking can add a Swift Package to your Xcode target or a Maven repository to your Gradle build. Use the script, or do them by hand.

Option A — the script (recommended)

From your app root:

npx yeofr-setup          # patches iOS + Android, then runs pod install
npx yeofr-setup doctor   # verifies every step

That is the whole native install.

Command Does
npx yeofr-setup both platforms, then pod install
npx yeofr-setup ios / android one platform
npx yeofr-setup doctor reports only, never writes
npx yeofr-setup --no-pods skip pod install
npx yeofr-setup --help usage

It is idempotent — re-run it after any upgrade and it changes only what is missing, including re-pinning the Swift Package when the bridge needs a newer engine. Every edit bails with an explanation if your project does not have the shape it expects, so it tells you to do a step by hand rather than mangling a file. It also knows where your project accepts repositories: if your Gradle setup centralises them in settings.gradle under dependencyResolutionManagement, the Repsy entry goes there instead of into android/app/build.gradle.

It needs Ruby with the xcodeproj gem for the Xcode edit — that ships with CocoaPods, so any project that can run pod install already has it.

Option B — by hand

iOS

  1. Open ios/<YourApp>.xcworkspace — the workspace CocoaPods generated, not the .xcodeproj.
  2. File ▸ Add Package Dependencies…, enter https://github.com/yeo-messaging/YEOFR-SPM.git, dependency rule Exact Version 0.7.8.
  3. When Xcode asks where to add the YEOFR library, choose your app target — not a Pods target. The bridge is a CocoaPods target and Pods cannot declare a Swift Package dependency, so your app target links and embeds the engine and the bridge picks the module up from the shared build products directory. Add it to the wrong target and the bridge fails to compile with no such module 'YEOFR'.
  4. In ios/Podfile, set platform :ios, '17.0' and paste the block below into your existing post_install, after the react_native_post_install call.
  5. cd ios && pod install (or bundle exec pod install if your project pins CocoaPods via a Gemfile)
    # No Intel simulator slice in the xcframework.
    installer.pods_project.targets.each do |t|
      t.build_configurations.each do |bc|
        bc.build_settings['IPHONEOS_DEPLOYMENT_TARGET'] = '17.0'
        bc.build_settings['EXCLUDED_ARCHS[sdk=iphonesimulator*]'] = 'x86_64'
      end
    end
    installer.aggregate_targets.map(&:user_project).uniq.each do |proj|
      proj.targets.each do |t|
        t.build_configurations.each do |bc|
          bc.build_settings['EXCLUDED_ARCHS[sdk=iphonesimulator*]'] = 'x86_64'
        end
      end
      proj.save
    end

    # Xcode 26 clang rejects fmt 11.0.2's consteval path.
    base_h = File.join(installer.sandbox.root, 'fmt', 'include', 'fmt', 'base.h')
    if File.exist?(base_h)
      src = File.read(base_h)
      needle = "#if !defined(__cpp_lib_is_constant_evaluated)\n#  define FMT_USE_CONSTEVAL 0"
      marker = "// Xcode 26 clang rejects fmt's consteval path"
      if !src.include?(marker) && src.include?(needle)
        File.chmod(0644, base_h) # CocoaPods checks pod sources out read-only
        File.write(base_h, src.sub(needle, "#if 1  #{marker}\n#  define FMT_USE_CONSTEVAL 0"))
      end
    end

Both halves of that block are required on Xcode 26, and each is a hard build failure without it. The EXCLUDED_ARCHS lines exist because the xcframework has no Intel simulator slice. The fmt patch is not our bug — every React Native 0.81 app hits it on Xcode 26 — but it surfaces during the same build and looks like a YEOFR failure. Drop it once React Native ships a newer fmt.

You also need NSCameraUsageDescription in your Info.plist if you use the camera. iOS prompts for camera access itself, but only with that key present.

Android

Add the Repsy repository to android/app/build.gradle — the app module:

repositories {
    mavenCentral()
    google()
    maven {
        name = "Repsy"
        url = uri("https://repo.repsy.io/mvn/samsonyeo/yeomessaging")
    }
}

This is not optional and npm i cannot do it for you. Gradle resolves a dependency's transitive artifacts against the consuming project's repositories, so the block inside the package's own android/build.gradle never applies to your :app. Putting it in the root project's buildscript.repositories does not work either — that only feeds the Gradle classpath. Without it the build fails with Could not find com.yeomessaging:yeofr-android:0.1.24.

Declare the camera permission yourself. The package's manifest declares no permissions — the frame API works with no camera at all, so whether your app carries the dangerous CAMERA permission on its Play listing is your call, not the library's. If you mount YeofrCamera, add <uses-permission android:name="android.permission.CAMERA" /> to your own manifest, and request the runtime grant too — the package never prompts. Mount YeofrCamera without the grant and it reports { type: 'error', failure: 'permissionDenied' } and draws nothing.

If your app is nothing but a recognition screen, also mark android.hardware.camera as a required feature in your manifest so the app cannot install on a camera-less device.

Commit these, once per repository

Steps 2–4 are a one-time change to the repo, not something each developer repeats. Commit ios/<App>.xcodeproj/project.pbxproj, ios/<App>.xcworkspace/xcshareddata/swiftpm/Package.resolved, ios/Podfile, ios/Podfile.lock and android/app/build.gradle, and everyone else — and CI — just builds.

Expo: the managed workflow has no ios/ directory to open, so run expo prebuild (or use a bare project) first. There is no config plugin yet.

Upgrading from 0.3.x

Three things changed for iOS hosts, all of which need action:

  • The engine is no longer vendored. ios/YEOFR.xcframework is gone from the package; add the YEOFR-SPM Swift Package to your app target (see Install) or the bridge will not compile.
  • Minimum iOS is now 17.0, up from 15.1 — raise platform :ios in your Podfile and IPHONEOS_DEPLOYMENT_TARGET on your app target.
  • Simulator builds need EXCLUDED_ARCHS[sdk=iphonesimulator*] = x86_64. Apple-silicon Macs only; there is no Intel simulator slice.

The JS API also changed, on both platforms:

  • createTracker() / freeTracker() are gone. The SDK owns the tracker's lifetime since activation was introduced; there is nothing to create or free. Delete both calls. If your freeTracker() was there to re-enroll from scratch, use clearTracker() instead; to persist and restore tracker state, use getTrackerData() / loadTracker().
  • Return codes are strings, and failures resolve instead of rejecting. loadTracker / clearTracker / enrollImage resolve "OK" on success and a platform failure string otherwise — they no longer resolve numbers, and no longer reject on an SDK failure. Old catch-based handling (iOS) and === 0 checks (Android) silently invert: migrate them to isOK(await loadTracker(...)).
  • enroll(faceID, name) is gone. Camera enrolment runs behind the bridge: set enrolName on <YeofrCamera> and wait for registered. Still-image enrolment stays as enrollImage.
  • Every SDK call now requires activate() first and rejects not_activated until it resolves.

The shortest migration diff:

// before (0.3.x)
await createTracker();
try { await enroll(faceID, name); } catch (e) { /* handle */ }
await freeTracker();

// now — activate once at startup, then enrol through the camera view:
await activate({pilotUnlockCode: PILOT_CODE});   // pilot code, both platforms
await activate({license: LICENSE});              // or a signed licence token (iOS only)
<YeofrCamera enrolName={name} onEvent={…} />     // 'registered' arrives when done
// nothing to free

Verify the install

getVersion() is the smoke test. It is the only call that works before activate() on both platforms, so it proves the native module actually linked.

import {activate, getVersion, isOK, clearTracker} from '@yeomessagingcom/react-native-yeofr';

console.log(await getVersion());                       // "0.7.8" iOS / "0.1.24" Android
await activate({pilotUnlockCode: 'XXXX-XXXX-XXXX-XXXX'});
console.log(isOK(await clearTracker()));
What you see What it means
getVersion() → a version string The bridge and engine are linked. Install worked.
undefined is not an object on getVersion The native module never registered — autolinking or pod install did not run.
activate rejects E_UNAVAILABLE_SIMULATOR Expected on the iOS simulator. This is a pass.
any call rejects not_activated activate() has not resolved yet. Everything but getVersion needs it.
the app dies at activation on iOS, no JS error Licensing — check your pilot code. See Licensing and pilot codes.

Licensing and pilot codes

The engine is commercial. Evaluation builds unlock it with a pilot code; shipping builds need a licence.

Using a pilot code

A pilot code is a time-limited string you pass to activate:

await activate({pilotUnlockCode: PILOT_CODE});  // e.g. 'XXXX-XXXX-XXXX-XXXX', issued by YEO

Do not hard-code it in shipped source. Codes expire, and a build that outlives its code stops activating — read it from your build config or fetch it at runtime, so a new code does not require a new binary.

Without a valid pilot code, an iOS build terminates at activation. It does not reject the promise — the process exits, so a try/catch around activate will not catch it and it presents as a launch crash. If your iOS app dies on startup, check the code before you look anywhere else.

license is the iOS-only alternative to a pilot code: a signed .yeolicense token, passed as activate({license}), for builds you intend to ship.

Pilot codes are issued for a fixed window and expire. Ask YEO for one covering the period you need, and confirm it is valid for both platforms before shipping a cross-platform pilot — do not assume a code that activates on one also activates on the other.

Getting a licence

Email christo@yeomessaging.com for a pilot code, or for the .yeolicense file and the licence agreement required to ship. A licence covers only the applications it names.

Using the SDK

The lifecycle is the same on both platforms even though the enrolment mechanics differ.

1. Activate, once, before anything else.

import {activate, UNAVAILABLE_ON_SIMULATOR} from '@yeomessagingcom/react-native-yeofr';

try {
  await activate({pilotUnlockCode: PILOT_CODE});
} catch (e: any) {
  if (e.code === UNAVAILABLE_ON_SIMULATOR) {
    // simulator: everything else still loads, recognition does not
  }
}

2. Restore any previous enrolment — the same call on both platforms:

const enrolled = await loadTrackerFromDisk();

3. Enrol a face. Set enrolName on the camera — on both platforms the native view captures the face in view and emits registered when done. Then persist with saveTrackerToDisk() — the same call on both platforms. See Platform differences.

4. Recognise. There is no recognise call — mount <YeofrCamera> and read result events as they arrive.

API reference

Every export is typed in index.ts and carries a doc comment, so your editor shows this inline. Promise-returning calls reject on native errors; the FRReturnCode ones resolve a status string instead.

activate(opts?: ActivateOptions): Promise<boolean>

Unlock the SDK. Must resolve before any other call except getVersion.

interface ActivateOptions {
  license?: string;          // signed YEO licence token, base64. iOS only.
  pilotUnlockCode?: string;  // time-limited pilot code. Both platforms.
}

Pass a pilotUnlockCode on both platforms; license is the iOS-only alternative for shipping builds. iOS requires one of the two and rejects immediately with activate requires a license or pilotUnlockCode if given neither. On the iOS simulator it rejects with code E_UNAVAILABLE_SIMULATOR.

getVersion(): Promise<string>

The engine version. Works before activate on both platforms.

clearTracker(): Promise<FRReturnCode>

Drop every enrolled face from the in-memory tracker. Does not touch anything persisted — pair with a fresh saveTrackerToDisk().

getTrackerData(): Promise<string>

The serialized tracker as base64, for your own storage or transport. Never rejects for an empty tracker once activated: iOS resolves the serialized empty form, Android resolves "" until something has been enrolled or loaded.

loadTracker(base64: string): Promise<FRReturnCode>

Restore a tracker previously obtained from getTrackerData.

Frame input

For hosts that capture their own images — an existing camera pipeline, a photo library, video stills — instead of mounting <YeofrCamera>. Both platforms, same signatures.

detectFaces(base64Frame: string, options?: DetectFrameOptions): Promise<FaceResult>

Detect + recognise + anti-spoof on one caller-supplied frame — the BYO camera tier. Resolves the same unified FaceResult the camera view emits, on both platforms.

interface DetectFrameOptions {
  rotationDegrees?: number; // quarter-turn rotation applied first, default 0
  mirror?: boolean;         // horizontal mirror applied after, default false
}

const result = await detectFaces(base64Jpeg);
if (result.status === 'trusted') console.log(`hello ${result.matchedName}`);

The contract:

  • After options apply, the frame must be upright and unmirrored (sensor space) — the space enrolled templates live in on both platforms. Set mirror: true only when your source is a preview-mirrored capture.
  • One frame source at a time. Never call this while <YeofrCamera> is mounted — both drive the same stateful engine tracker.
  • A few frames per second, not video-rate. Frames cross the bridge as base64-encoded images (JPEG/PNG); the first call also pays a one-off engine warm-up.
  • Liveness runs, depth never does — depthIsThreeD is always null on a fed frame (there is no sensor behind it). And because the caller controls the frames, a replayed stored frame defeats liveness by construction. <YeofrCamera> remains the surface for access-control decisions.

The engine keeps short-lived state across calls (a liveness hold bridges the odd unscoreable frame), so treat consecutive calls as one stream, not independent verdicts.

The two calls below are recognition only. Neither runs liveness or depth, so neither can tell a live face from a photograph of one. Use them for offline accuracy work and reference enrolment, never as a standalone unlock decision.

matchImage(base64Image: string): Promise<ImageMatch>

Grade a probe image against the enrolled gallery.

interface ImageMatch {
  matched: boolean;          // accept decision at the still-image operating point
  similarity: number | null; // best score in [0, 1]; null when unscoreable
}

const {matched, similarity} = await matchImage(base64Jpeg);

base64Image is an encoded image (JPEG or PNG), not raw pixel data — the bridge reads its dimensions itself. Rejects bad_input when it does not decode.

similarity is null — with matched false — when there is no enrolled gallery, no detectable face, or the match call fails. It is always null on Android, whose engine reports a decision rather than a score, so branch on matched and treat the score as diagnostic. On iOS only the largest face is graded, so a group photo containing the enrolled user still matches.

enrollImage(base64Image: string, name: string): Promise<FRReturnCode>

Enrol a reference identity straight from a still image, no camera, so matchImage has something to grade against.

if (isOK(await enrollImage(base64Jpeg, 'ada'))) { /* reference added */ }

Resolves imageNoFaceDetected when the image carries no usable face — the same spelling on both platforms, so one check covers you. The template lands in the recognition gallery, so matchImage, detectFaces, and <YeofrCamera> all recognise the identity. Persist the result like any other enrolment: saveTrackerToDisk on both platforms.

Return codes — FRReturnCode and isOK

type FRReturnCode = string;
const isOK = (code: FRReturnCode): boolean => code === 'OK';

The spellings that genuinely coincide on both platforms are "OK", "imageNoFaceDetected", "cannotCreateFile", "incompatibleTrackerData" and "legacyTrackerRejected" — the engines share that numbering. Outside it the platforms diverge: iOS collapses unrecognised engine codes onto its own cases ("trackerIsNull", "nativeException", or a catch-all), Android reports them as "error(N)". iOS appends the rejected envelope version to legacyTrackerRejected ("legacyTrackerRejected(version: 3)"). So: test success with isOK, and match failure families with startsWith(...) rather than exact comparison.

if (isOK(await loadTracker(blob))) { /* restored */ }
if ((await loadTracker(blob)).startsWith('legacyTrackerRejected')) { /* re-enrol */ }

Persistence — both platforms

saveTrackerToDisk(): Promise<boolean> and loadTrackerFromDisk(): Promise<boolean> resolve false when there was nothing to write or nothing stored — one pair, both platforms. Android writes app-private filesDir/tracker.bin; iOS writes the tracker into Application Support.

Anti-spoof signals

Both anti-spoof signals — the liveness CNN and, on iPhone, the TrueDepth 3D check — are always on. The package exposes no toggle for them, matching the Flutter plugin's surface; a spoofed frame simply reports notTrusted.

Camera component

import {YeofrCamera} from '@yeomessagingcom/react-native-yeofr';

<YeofrCamera
  style={StyleSheet.absoluteFill}
  onEvent={(e) => handle(e.nativeEvent)}
/>

Call activate() before mounting. The capture session — lens, resolution, backpressure, orientation — belongs to the package; the component places the preview and reports one event per analysed frame.

Props

Prop Type Platform Meaning
onEvent (e: NativeSyntheticEvent<CameraEvent>) => void both Every frame result, enrolment completion and error
enrolName string both Non-empty captures the face in view and enrols it under that name; clearing it cancels. Anti-spoof is pinned on natively while it runs. Persist afterwards with saveTrackerToDisk
enrolPoses EnrolPose[] both The pose walk a capture runs, in order ('front', 'yawLeft', 'yawRight', 'pitchUp', 'pitchDown'); read when a capture (re)starts. Omit for the plain single front capture. Progress arrives as enrolProgress events
lensFacing 'front' | 'back' Android Default 'front'. Changing it restarts the session
minFrameIntervalMs number Android Smallest gap between analysed frames. Frames are dropped before conversion, so raising this saves the work. Default 0
analysisResolution string Android Preferred analysis resolution as 'WIDTHxHEIGHT'; omit to let CameraX choose

It also accepts all standard ViewProps.

Events

type CameraEvent =
  | ({ type: 'result' } & FaceResult)
  | ({ type: 'enrolProgress' } & EnrolProgress)
  | { type: 'registered'; name: string }
  | { type: 'error'; failure: CameraFailure };

interface EnrolProgress {
  phase: 'capturing' | 'completed' | 'failed';
  pose: EnrolPose;          // what the user should be doing right now
  posesAccepted: number;    // fills a progress ring: accepted / planned
  posesPlanned: number;
  isTargetMatched: boolean; // iOS: the user is holding the pose; Android: the frame passed the capture gate
}

enrolProgress steps arrive once per analysed frame while a capture runs; a final completed step precedes registered, and failed precedes the enrolFailed error. The app owns the prompt wording for each pose.

interface FaceResult {
  faceState: FaceState;
  detectedCount: number;
  status: 'noFace' | 'badFraming' | 'notTrusted' | 'trusted';
  matchedName: string | null;
  livenessGenuine: boolean | null;  // iOS: SDK-thresholded; Android: LivenessHold over isConfident
  depthIsThreeD: boolean | null;    // Android: always null — no sensor. The one honest residue.
}

The same shape on both platforms: iOS computes the verdict inside the SDK's frame loop, Android computes it in the bridge (framing gate, liveness hold, recognition), and JS never sees rects, raw scores or thresholds on either.

One CameraFailure vocabulary on both platforms: 'permissionDenied', 'noCameraForLens', 'bindFailed', 'noLifecycleOwner', 'notActivated', 'enrolFailed'. permissionDenied, bindFailed, notActivated and enrolFailed can occur on either platform; noCameraForLens and noLifecycleOwner only arise on Android's capture stack.

Platform differences

The JavaScript API is one surface, but it is not uniformly implemented. This is the section to read before designing your screens.

Capture model

The two native SDKs do not offer the same capability, and this is the root of every camera difference below.

iOS engine 0.7.8 Android engine 0.1.24
Camera ownership Yes — the SDK runs its own AVCaptureSession and exposes a frame stream No — the SDK owns no camera at all
Frame input Yes — frames and still images can be fed in directly Yes — detectFaces(ImageFrameParameters) is the entire public entry point

So: iOS supports both camera and frame input; Android supports frame input only. Because the Android engine has no camera, the React Native bridge supplies one itself — it runs a CameraX pipeline, converts each frame, and calls the engine's frame API. That is why <YeofrCamera> renders on both platforms despite only one engine owning a camera.

Frame input from JavaScript works on both platforms. detectFaces runs the full per-frame verdict on a frame your own pipeline produced; matchImage / enrollImage grade or enrol from stills. See Frame input. The JavaScript contract is identical on both; the bridge does whatever each engine needs underneath.

Who owns capture leaks into the props:

iOS Android
Owns capture The SDK, via its own AVCaptureSession — required for the TrueDepth signal; the bridge attaches a preview layer The bridge, via CameraX, standing in for a camera the engine does not have
Lens Fixed by the SDK lensFacing, default front
Frame cadence Fixed minFrameIntervalMs
Resolution SDK picks analysisResolution
Prop change Mutates the running session Restarts the session
Camera permission iOS prompts via NSCameraUsageDescription Your app declares CAMERA and requests the grant

The only prop both platforms share is onEvent. Passing an iOS prop on Android, or the reverse, is silently ignored.

Enrolment

Both platforms follow the same shape — capture, then registered, then the app persists — but the capture runs in different places, because only Android surfaces per-face ids to JavaScript.

Set enrolName and the native view captures the face in view (anti-spoof signals are forced on in native code while it does — no JS config can relax them), then emits registered; a new name restarts the capture. Persist afterwards with saveTrackerToDisk() on both platforms. On iOS the SDK's own enrolment machinery runs the capture; on Android the bridge collects 20 frames that pass framing and liveness and enrols from the first.

Add enrolPoses and the capture becomes a guided walk through those prompts, reported step by step over enrolProgress. The walk is verified on iOS — the engine measures head angles, a pose only accepts while it is genuinely held, and a pose the user cannot hit self-resolves after a few seconds so the walk never wedges. Android's engine exposes no head pose, so there the same prompts pace the capture instead: the frame budget is split evenly across the poses and each advances after its share of good frames, banking whatever varied appearance the user actually shows. On iOS a sequence that ends with a second 'front' additionally runs the engine's lighting pass during that final step.

Clearing enrolName cancels the capture's events on both platforms — not the capture itself. Android commits the identity to the gallery on that first good frame and the engine has no un-enrol call; the iOS walk has no cancel either and, with a face still in view, can run to completion headless. Treat cancel as "stop listening", not "undo" — an app that must undo an abandoned capture restores its persisted tracker (loadTrackerFromDisk) or clears it.

Reading a frame result

Both platforms hand you a decision: read status === 'trusted' and matchedName, and keep any extra display logic out of the render path. Under the hood iOS's SDK computes the verdict itself, while the Android bridge derives it from the engine's raw signals — including the engine's own framing rule (a face at least 20% of frame width, at least 2% inside each edge) and a short liveness hold across frames the engine declines to score. Neither platform surfaces rects, scores or thresholds to JS.

The example app

The demo is FRPilot rebuilt in React Native: activate → enrol → recognise, with trust signals on screen.

The camera ships inside the package, so the demo's JavaScript runs from the published tarball — there is no missing native component to register. example/App.tsx and example/src/ are already in your node_modules.

The demo mounts a single <YeofrCamera> and lets each platform resolve it to whichever path its engine supports: on iOS that is the SDK's own camera session, on Android the bridge's CameraX pipeline feeding the engine's frame API. There is no frame-API screen — frame input is for images your own pipeline produced, and the demo's camera flows exercise the camera path.

What it does, screen by screen

Hub. On mount it calls activate({pilotUnlockCode: PILOT_CODE}) and getVersion(), then restores any prior enrolment with loadTrackerFromDisk() — the same call on both platforms. It shows one of three states: Unavailable (simulator), Unlicensed (activation error), or Activated with a name field and two buttons — the same on both platforms.

Camera screen (enrol or recognise). On Android it requests PermissionsAndroid.PERMISSIONS.CAMERA on mount and renders nothing until granted. In recognition mode a bottom badge shows the headline in green when trusted, red otherwise. In enrol mode it shows a prompt and an Enrol button enabled only when the current frame is good enough.

The two logic files worth copying

trustPolicy.ts turns a frame into a verdict, in strict order: no face → multiple faces → bad framing → liveness (unverified vs spoof) → unrecognised → trusted. Framing is checked before liveness deliberately, so an unscored frame is never reported as a spoof. canEnrol allows enrolment only when the verdict is trusted or specifically unrecognised — never on a spoof, unverified or badly framed face — and enrolment always evaluates with liveness forced on, whatever the switch says.

The liveness debounce that used to live beside it (livenessHold.ts) moved below the bridge with the verdict itself: LivenessHold in the Android bridge's TrustPolicy.kt and FrameLivenessHold in the iOS bridge's FramePolicy.swift. When a frame cannot be scored they hold the previous liveness answer for up to 3 frames, then fall back to unverified rather than spoof. The Android policy is pinned by JVM tests in android/src/test/java/com/yeofr/TrustPolicyTest.kt.

Running it

Clone the repo — the demo's host projects (example/ios, example/android) are repo-only — then work from example/ (every command below; yeofr-setup fails with "no ios/*.xcodeproj" if run from the repo root):

npm install                      # at the repo root — the example is an npm workspace
cd example
npx yeofr-setup                  # validates the config, runs pod install
npm start                        # Metro

npm run android                  # Android
npm run ios -- --device          # iOS: use a device, recognition is inert in the simulator

Note the -- before --device: without it npm consumes the flag instead of passing it to the CLI. The iOS workspace is example/ios/YeofrDemo.xcworkspace and already references YEOFR-SPM at an exact version; Xcode resolves it on first open. Signing is pre-configured with the YEO team — pick your own in Signing & Capabilities only if you are not on it. PILOT_CODE in App.tsx is a placeholder — replace it with a real code before running on iOS, where an invalid one kills the process.

Ruby: the repo pins bundler via Gemfile.lock, and run-ios insists on running bundle install itself — macOS's system Ruby is too old for it. Use Homebrew Ruby and install the pinned version once:

echo 'export PATH="/opt/homebrew/opt/ruby/bin:$(/opt/homebrew/opt/ruby/bin/gem environment gemdir)/bin:$PATH"' >> ~/.zshrc
source ~/.zshrc
gem install bundler:2.6.3   # match the BUNDLED WITH version at the bottom of example/Gemfile.lock (2.6.3 at the time of writing)

The example installs as an npm workspace, so npm hoists most packages to the repo root; the Android gradle files resolve the RN plugin and codegen through Node, which finds them in either layout. If a clone from before that fix reports Included build …/@react-native/gradle-plugin does not exist, pull — or symlink the hoisted package into example/node_modules as a stopgap.

Copying the demo into your own app

Three things break if you copy the files without the host projects:

  1. faceEvents.ts imports FaceResult from '@yeomessagingcom/react-native-yeofr' — already the published name, so this one now copies cleanly.
  2. iOS needs NSCameraUsageDescription in your own Info.plist, or the camera never prompts and the session fails.
  3. iOS needs the Podfile post_install block from Install — that is what npx yeofr-setup writes for you.

Troubleshooting

Symptom Cause and fix
no such module 'YEOFR' at build time The Swift Package is on the wrong target, or declared but not linked. Run npx yeofr-setup doctor.
unable to resolve module dependency: 'YEOFR' on the simulator The EXCLUDED_ARCHS half of the post_install block is missing.
call to consteval function … is not a constant expression in fmt Xcode 26 vs React Native 0.81's pinned fmt. The post_install patch fixes it; it is not a YEOFR bug.
Could not find com.yeomessaging:yeofr-android The Repsy repository is missing from android/app/build.gradle.
SDK location not found Standard React Native setup — set ANDROID_HOME or sdk.dir in android/local.properties.
cannot load such file -- xcodeproj from the script Ruby lacks the gem — gem install xcodeproj, or bundle install in ios/.
undefined is not an object calling any API Native module not registered — autolinking or pod install did not run.
Every call rejects not_activated activate() has not resolved yet.
iOS app dies at launch with no JS error An expired or invalid pilot code. iOS terminates rather than rejecting.
Camera renders nothing on Android, permissionDenied event Your app must declare CAMERA in its manifest and request the runtime grant; the package never prompts.
enrolName never emits registered The capture only counts frames that pass framing and liveness — fill the frame, hold still, good light.
